# App: tray, popover, taskbar display, steering, settings

Crate `crates/subhub-app` (GPUI). Domain logic lives in `crates/subhub-core`; the app only renders state and calls core on background threads. Decisions: ADR 0001 (incl. "Refinements 2026-11-06").

## Lifecycle

- One instance (named mutex `Local\AISubHub.SingleInstance`); a second start exits. Development builds (cargo `target\debug|release`) use `Local\AISubHub.SingleInstance.Dev`, so one can run next to the installed app for testing (2026-11-07). For a test run, point `LOCALAPPDATA` at a sandbox folder (settings, history, caches follow it) and switch the hub and steering off in that copy: the hub key is in Credential Manager, which a dev build shares, and steering writes hub priorities.
- `QuitMode::Explicit`: closing windows keeps the app running (unless General → Close button says Quit completely); Quit is in the tray menu. If the tray icon cannot be created the app quits at once.
- First start with no accounts opens Settings on Accounts → Add accounts.

## Demo mode (2026-11-07)

Core: `subhub-core/src/demo.rs` (fixtures, deterministic for a given time, tested); app: `subhub-app/src/demo.rs` (the flag) plus small guards where something would leave the process.

If the sandbox cannot be set up, the app does not start.

Codex Personal's access ends in 12 days (canceled). For the Overview (scan v2, 2026-11-07) the history follows `demo::PATTERNS`: readings every 15 min while the "PC" is on (07:00-18:30 UTC weekdays, Saturday mornings), weekly cycles that drop at each reset, Personal (Pro) running out 3 h into its 08:00 window on Mon/Wed/Fri while Work had room, Team hitting on Tue/Thu, Work (Max 20x) peaking near 20 % of its week, Side project (benched) idle and added 12 days ago, Codex Personal's late windows outliving the PC (unknown ends), resets with seconds of jitter. The logs carry `tool_use` blocks of every task kind with made-up commands, subagent files (`isSidechain`), `cwd` inside the demo projects (some in `scratch\notes`, a few without), and `custom-title` lines; there is still no message text. `demo::tests::history_tells_the_overview_story` pins the verdicts, tips and warm-up this produces.

- Works with `--show-whats-new`; `--demo --stats-dump [path]` dumps the demo logs.
- `--demo --demo-page <page>` opens a window at start, for screenshots without clicking: `general`, `appearance`, `accounts`, `add-accounts`, `hub`, `projects`, `about` (Settings) or `stats`. ## Logo and icons

- Logo (`logo.rs`): static skeleton badge on a 16-unit grid (Claude-orange dot, orange tag pill overlapping its lower edge with a small gap, long blue bar over short amber bar on grey tracks), rendered with 4x4 supersampling. Used for the tray icon (32 px, never live), window icons (`logo::window_icon`, 64 px) and the exe (`assets/app.ico`, 16–256 px PNG entries, written by `ai-subhub --write-icon <path>`, embedded by `build.rs` via `app.rc`). Regenerate the .ico after changing the geometry.
- UI icons (`icons.rs`): Lucide SVGs from gpui-component's `gpui-kit-assets` (refresh-cw, settings, x, star, arrows, plus, info, eye, trash, check) plus own provider marks (`assets/icons/provider-claude.svg`, `provider-openai.svg`), served by `assets::Assets`; single-colour, tinted via `text_color`. No text characters as icons.

## Tray icon

- Own `Shell_NotifyIconW` module (`tray.rs`, `NOTIFYICON_VERSION_4`). Left click (`NIN_SELECT`) toggles the popover; right click (`WM_CONTEXTMENU`) opens Open / Refresh usage / Settings / Quit. Only one of each click pair is handled (a click also sends `WM_LBUTTONUP`; handling both opened and closed the popover at once).
- Icon: the static logo. Tooltip: just "AI SubHub", Windows' plain tooltip like other tray apps (owner, 2026-11-07: the usage is one click away in the popover; the earlier usage text and the tray hover card were removed).

## Hover cards (2026-11-07)

**Tray icon: plain text tooltip again (owner, 2026-11-07).** The hover card over the tray icon was removed: the tray always sets `NIF_SHOWTIP` and the tip is just "AI SubHub", `NIN_POPUPOPEN` / `NIN_POPUPCLOSE` / `WM_MOUSEMOVE` are ignored. Hover cards remain for the taskbar badges only; the tray parts below are historical.

Core: `subhub-core/src/hover.rs` (card model: per account 5h then weekly window, other windows only when neither exists, health Fresh/Stale/Cooling down/Sign in needed/CLI missing/Benched/No reading yet, steering role, "+N more"; tip text) and `placement.rs` (`card_origin`). App: `hover_card.rs`. Owner request: the grey native tooltip "isn't looking good".

- A small window styled like the popover (app theme, DWM rounding/outline, Segoe UI Variable, provider mark in `icons::series_color`, tag chips, mini bars, "% left"/"% used", reset countdown, "Stale · 15m ago" pill, steering pill) that shows while the pointer rests on the **tray icon** (all visible accounts in settings order, at most 6 then "+N more · click to open", header "AI SubHub" + "Updated …") or on a **taskbar badge** (that account, plan in the title, footer "Updated … · click to open"). Fixed widths 300 / 264 px; fixed row heights so the height is known before drawing (`card_height`, tested). Never focused; one card at a time.
- Showing: tray `NIN_POPUPOPEN` (Windows' own hover delay; `NOTIFYICON_VERSION_4` without `NIF_SHOWTIP`), with a `WM_MOUSEMOVE` fallback (rest 400 ms) in case a Windows build does not send it; badges after 400 ms (GPUI `on_hover`; each account's painted area is recorded with a `canvas` so the card anchors to it). Moving from one source to another (badge to badge, badge to tray) switches the card at once.
- Hiding: `NIN_POPUPCLOSE`, a click or drag on the display, the popover opening (`toggle_popover`), the setting switched off, or the **watchdog**: every 100 ms, two checks in a row with the pointer off the anchor (3 px slack) hide it, since Windows does not always send the close. No card while the popover is open or a fullscreen app is in front.
- Placement (`placement::card_origin`, tested): centred on the anchor (tray icon: its real rect, also inside the overflow flyout, `Tray::icon_rect`; the popover keeps using the notification area), 8 px from it on the desktop side (above a bottom taskbar, below a top one), 12 px inside the anchor monitor's work area on the other sides; all physical px with the anchor monitor's scale.
- One card window per monitor: it is opened on the anchor's monitor (`display_id`, shown at once) and reopened when the next anchor is on another monitor. Moving a GPUI window onto another monitor inside a GPUI update re-enters GPUI (WM_MOVE → display change → `AsyncApp::update`) and panics; seen 2026-11-07 with both the taskbar display and the card. A hidden window stays on the default monitor until shown, so the card is created visible.
- Setting: Appearance → More options → "Show details on hover" (`display.hover_details`, default on): cards over the taskbar badges. Off: nothing on the badges. The tray icon always shows the plain text tooltip.
- Verified 2026-11-07 (dev build, sandboxed `LOCALAPPDATA`, two 2560x1440 monitors): badge card after the delay, switching between badges, hiding when the pointer leaves, stale pill, card on the second monitor's taskbar, tray card (all four accounts) after a posted `NIN_POPUPOPEN`, reopening on the other monitor. Not verified: a real hover over the dev tray icon (Windows 11 keeps new icons hidden in the overflow until allowed in taskbar settings, and its icon did not get pointer events there); check with the installed build.

## Popover (layout A)

- Borderless `WindowKind::PopUp`, opaque, native Windows 11 rounded corners/outline/shadow via DWM (`window_style.rs`). 460 px wide; height fits the content (240–720 px, more scrolls) and re-fits upwards via `SetWindowPos` when content changes (GPUI `resize` keeps the top edge). The current height is read from `GetClientRect`: GPUI's viewport size lags a frame, and quick changes (a layout setting toggled back and forth) piled up stale deltas until the popover collapsed. The layout is always the comfortable one (the Density setting was removed, owner 2026-11-07: the popover is resizable by its top edge). Centred on the tray icon (or the notification area when the icon is in the overflow), 12 px inside the monitor work area.
- Stays open until the tray icon, Esc or ✕; Appearance → "Close popover when clicking elsewhere" (off by default) restores close-on-focus-loss with a 300 ms reopen guard.
- Header: "AI SubHub", "Updated … · next in …" (or Updating… / hub key problem), ↻ (refresh now: skips backoff, never a provider cooldown), ⚙ Settings, ✕.
- Provider headings, one card per visible account: name, plan pill, group, source tags, status tag (Stale / Cooling down / Sign in needed / CLI missing), freshness dot + "Xm ago"; one row per visible window: label, bar, "% left" (or "% used"), reset as a countdown ("2d 4h") with the exact local time in its tooltip ("Resets Sat, Nov 8, 14:30"; the Exact format setting was removed 2026-11-07). Warning colour at 25% left or less (`RUNNING_OUT_PERCENT`, fixed), red at 10%. Stale cards are dimmed with the last reading time and message; cards without a reading this session explain the saved schedule ("Usage checks cooling down · next try in …").
- Source tags: **Hub** (shows the steering state, not clickable: "Hub · preferred" when picked, "Hub · next" for the current Auto target), **Hub · benched**, **Local only** (CLI profile, not in the hub). A CLI profile next to a hub login gets no pill (owner, 2026-11-07: both are the normal case; Settings still names the source).

## Taskbar display

- `taskbar.rs`: borderless, topmost tool window over a free part of the taskbar (Windows has no API for third-party taskbar content; TrafficMonitor-style). Right (default): left of `TrayNotifyWnd`, or 380 px from the right edge when Windows 11's XAML taskbar has none (this PC); Left: 176 px from the left edge (centred taskbars only; collides with left-aligned icons). Drag it along the taskbar to move it; the spot is saved as `taskbar_offset` (px from the taskbar's right edge) and choosing Left/Right resets it. A short press without moving is a click. Starts 2 px below the taskbar top so its top border stays visible, then fills the rest; re-raised every second (the taskbar comes to the front when clicked), and hidden while a fullscreen app is in front (`SHQueryUserNotificationState` busy/D3D/presentation, or the foreground window covers its monitor; desktop and taskbar excluded). Before this it covered fullscreen videos and games (owner, 2026-11-06); verified hidden with Chrome fullscreen. Vertical/hidden taskbars are not supported. Click toggles the popover.
- On/off (Appearance → "Show usage on the taskbar", `display.taskbar_enabled`, default on; owner 2026-11-07): off closes the display and leaves just the tray icon; the style and the other taskbar rows are kept and hidden while off. Older files with the style `Off` load as switched off + Badge (`settings_store::sanitize`).
- Style (Appearance → Style): **Badge** (default, also for files without the field; before 2026-11-07 `DisplaySettings::default()` said Bars by mistake; like T3 Code's provider tags: left block over both rows = provider icon (Claude orange ✻, Codex ◎) with the coloured two-letter account tag overlapping its bottom-right corner, 1:1 the T3 Code sidebar style (owner, 2026-11-06), right block = "5h bar %" over "W bar %"; integrated like tray icons (owner, 2026-11-06): no boxes, full height, rounded hover highlight per badge, thin dividers left and right of the group, tag centred on the icon's bottom edge, steering target marked by a small accent bar under the icon like Windows' running-app marker (under the whole badge it read as a third row); labels no-wrap (a 12 px column broke "5h")), and **Bars** (name + %, then the 5-hour bar). Numbers and Focus were removed (owner, 2026-11-07); old Mix/Blocks load as Bars, Table/Numbers/Focus as Badge.
- Typography matches the taskbar clock (owner, 2026-11-06): Segoe UI Variable Text, 12 px, regular, two 16 px lines, full-contrast text. No fill: the window is transparent and skips gpui-component's `Root` (it paints the theme background); `window_style::no_frame` removes the Windows 11 popup frame (border colour none, no rounding). Faint fill only on hover. Verified 2026-11-06: pixels inside the display match the taskbar next to it, so custom taskbar colours show through. Text/bar colours follow the Windows mode (`SystemUsesLightTheme`, taskbar/Start), not the app mode, re-checked every second.
- How many (Appearance → Accounts, "up to", hidden for Focus): 1–5, default 3.
- Monitors (Appearance → More options → Monitors, `display.taskbar_monitors`, owner 2026-11-07): **Main taskbar** (default; `Shell_TrayWnd`, where the tray icon is), **All taskbars**, or **Choose** (one switch per connected monitor, "1 · XF272U", "2 · LG ULTRAGEAR+ (main)", numbered left to right; starts with the main one). Other monitors need Windows' "Show my taskbar on all displays" (`Shell_SecondaryTrayWnd`); a monitor without one shows "No taskbar on this monitor right now." Monitors are saved by their stable id: the monitor device path from `QueryDisplayConfig` (`monitors.rs`), the GDI name (`\\.\DISPLAY2`) only as fallback. Which taskbars get a display is `placement::display_monitors` (tested): chosen monitors that are missing are skipped, and when none is there the main taskbar is used until one comes back (owner: fall back to main). One window per monitor; `sync_taskbar` re-checks every 3 s and on state changes (docking, plugging). Each window is opened on its monitor (`display_id`, see Hover cards) and re-placed every second when its taskbar moves or the scale changes.
- Drag position per monitor (owner 2026-11-07): `display.taskbar_offsets` (monitor id → px from that taskbar's right edge); the main taskbar falls back to the older single `taskbar_offset` until it is dragged again; Left/Right resets all. Default spot on another monitor's taskbar (no tray icons there): 160 px from its right edge, next to the clock.
- Tags: own tag per account on its page in Settings → Accounts (1–3 characters, kept as typed, empty = automatic two letters from the short name); stored in `settings.account_tags`. Colour stays fixed per account id. Example: WRK, PER, SID.
- Which accounts (Appearance → Accounts): Favorites (default; ☆/★ on each popover card, first N in star order, shown even before their first reading with "—"; the steering target when none is starred), Focus (steering target only), Auto (steering target + accounts with a window at 25% left or less, up to N). Never blank: falls back to the first account with a reading. The steering target gets a dot. Short names: the part after " · " of auto-made labels ("gmail"), else 10 chars.
- `window_style::set_bounds` corrects for the popup's invisible frame (`SetWindowPos` takes the outer rect); without that every re-place after a refresh moved the display ~10 px up, half above the taskbar (seen 2026-11-06).
- GPUI's default line height is too tall for three lines in a ~40 px taskbar; the display sets 11 px.

## Hub steering

- Choosing the account (owner, 2026-11-07: "clicking on a Hub badge isn't it"; option B of three previews): each popover card has a **⋯** button next to the rocket and the star. Its menu has **Use for new hub threads** (turns steering on if it was off) or, on the preferred account, **Back to Auto**, for hub logins that are not benched, and **Account settings…**, which opens Settings on that account's page. The Launch dropdown and the ⋯ menu share one floating-card implementation (`CardMenu`, one open at a time). The switch on the account page in Settings stays.
- After each refresh and when the preferred account changes, `AppState::steer`: `steer::target` (off → none; preferred → it; else Auto: highest weekly % left ÷ hours to weekly reset among hub accounts that are not benched/hidden/stale and have ≥ 5% of the 5-hour window, 25% hysteresis) → `steer::plan` → background `HubClient::set_priority` (`PATCH /v0/management/credentials/fields {name, priority}`, fallback `auth-files/fields` on 404). Originals are saved only after all writes succeed; failures show in Settings → Hub.
- Verified 2026-11-06 on the installed hub: Auto picked the account whose weekly reset came first and the hub listed `priority=100` for it, others unchanged.
- Applies to new threads of every hub client (T3 Code's Hub provider, other hub-backed CLIs and servers, Codex Hub); session affinity keeps running threads on their account. Turning steering off restores original priorities.

## Refresh

`AppState::refresh`: list the hub (when on and a key is stored) → `merge::apply_hub_accounts` → read due accounts in parallel threads (`refresh::read_account`: hub first, profile fallback) → apply results (schedule, reading, email, plan) → `merge::fold_duplicates` → save → steer. A 30 s timer calls it; each account's persisted schedule decides whether it is due.

- Hub cooldown per login: a hub 429 for an account that also has a CLI profile reads the profile in the same round and skips the hub for that account until `retry_after` (default 10 min); `AppState::hub_cooldown`, not persisted. Folding keeps tag, star and steering choice.
- A 401/403 through the hub means the hub's login was not accepted (seen 2026-11-06: Codex `token_expired` on a hub login never used through the hub). SubHub never renews tokens.
- No duplicates (owner rule, 2026-11-07): Add account reads the profile's login email from its own metadata (`profile::profile_email`: Claude `.claude.json` oauthAccount.emailAddress; Codex `auth.json` id_token payload, email claim only) and attach the profile to the existing account with that email (keeping name, tag, star, order, readings); an already connected folder or a login that already has a profile is skipped.
- Tag colours: 8 clearly different hues; each account prefers the slot from its login email (stable across merges), else the id, and takes the next free slot when an earlier account (settings order) has it, so no two accounts share a colour (`taskbar::tag_slot`).
- `fold_duplicates` merges a hub-only account into a profile account that just learned the same email (a profile whose email is not known yet).

## Add accounts (profile detection, 2026-11-07)

Core: `subhub-core/src/profile.rs` (`discover_dirs`, `profile_email`), `subhub-core/src/detect.rs` (statuses, `attach_profile`, `import`, `default_label`). UI: Settings -> Accounts -> Add accounts (`settings_window.rs`; until 2026-11-07 its own menu entry "Detect / Import"), `AppState::detect_profiles` / `import_profiles`. Decisions: ADR 0001 ("Profile detection", "Settings distilled").

- **Where**: every folder in the user folder whose name starts with `.claude` / `.codex` (sorted, so the defaults come first), then the folders in `CLAUDE_CONFIG_DIR` (comma-separated, `~` expanded) and `CODEX_HOME`, then `%XDG_CONFIG_HOME%\claude` or `~\.config\claude`. Canonical (junctions resolved), stored without the `\\?\` prefix, each folder once per provider. The statistics scan uses the same `discover_dirs` (and keeps only `projects` / `sessions`).
- **What counts**: Claude folders with `.claude.json` or `projects`, Codex folders with `auth.json` or `sessions`. The email comes from `profile_email` only (no token is read or kept); the default `~\.claude` falls back to `~\.claude.json`, where Claude Code keeps it without `CLAUDE_CONFIG_DIR` (this also fixes Add account for that folder).
- **Tabs** (owner, 2026-11-07): **CLI profiles** (default) and **Hub**, as segmented chips under the heading.
- **One account per login** (owner, 2026-11-07): a login in both the hub and a CLI folder stays one account with both sources (hub first, profile as fallback; Launch and Sign in use the profile). The user is informed, not asked to choose.
- **CLI rows** (grouped by provider): checkbox, email in bold (folder name when none), path. Importable rows have no tag (owner, 2026-11-07: the user recognises the login and ticks it; whether the import creates an account or links the profile to the account that already has this login, usually from the hub, is internal; core still tells `New` from `Joins`). Only the exceptions are tagged: **Already added as <name>** (no checkbox, dimmed), **Same login as <folder>** (a connected or earlier folder has this login; never imported), **No login found** (folder without an email); plus the note **Also in the hub** when the login's account has a hub login. Rows with an email are ticked when the page opens; no-login rows are importable but unticked. A linked account keeps its name, tag, star, order and readings.
- **Hub tab** (read-only): "Source: CLIProxyAPI hub at <address>", the hub status ("4 logins in the hub, added automatically on each refresh", or what is missing, with a Hub settings button) and one row per hub account with **Also as CLI profile <folder>**, **CLI profile <folder> found, not imported** or **Hub only**, plus **Benched**. Hub logins are not imported here: `merge::apply_hub_accounts` adds them on every refresh, as before.
- **Actions**: Select all, Select none, Detect again, **Import selected (N)**. Ticking saves nothing (the one exception to save-on-change, like Add account); Import attaches each pick through `detect::attach_profile` (also used by Add account, so the no-duplicates rule lives in one place), saves, refreshes, opens the first new or linked account and shows a toast ("Imported 4 profiles.", new and linked counted together). Names: the email's local part, with the domain when the provider already has that name ("me · corp"), else the folder name without the dot.
- **When**: detection runs each time the page opens and on Detect again, and the statuses are recomputed when the account list changes while the page is open (ticks on rows that stay importable are kept). Without that, a first start showed "New" for profiles whose hub login the first refresh added a moment later (seen 2026-11-07); no background watching, no ignore list (a removed profile shows as New again). No profiles found: the "Choose a folder manually…" form starts open.
- Verified: tests in `profile.rs` and `detect.rs`; a read-only dry run on the owner's PC (2026-11-07) found `.claude`, `.claude-gmail`, `.claude-gmail-tavora` and `.codex` with logins, and `.claude-hub`, `.claude-sub-gmail` and `.codex-hub` without. Not yet run in the UI (the installed app held the single-instance mutex).

## Sign in, Retry and Tools

Core: `subhub-core/src/launch.rs` (pure command building, tested without a terminal), UI in `settings_window.rs`, `popover.rs`, `state.rs`.

Asked during a running refresh, it runs right after it. Not offered for sign-in-needed accounts (Sign in instead) or during a cooldown, like the C# `UsageRecovery`.
- **General → Advanced** (the former Tools page, a collapsed disclosure since 2026-11-07): Sign-in terminal (Windows Terminal / PowerShell; Windows Terminal is auto-detected via `wt.exe` on PATH, PowerShell is used when it is missing), Claude CLI and Codex CLI path inputs (empty = auto-detect: `~/.local/bin`, npm global, PATH, Codex desktop bundle; saved on Enter or blur; must be an existing .exe/.cmd/.bat), each with "Found: path" / "Not found". ## Updates (2026-11-07)

Core: `subhub-core/src/update.rs` (versions, release JSON, sha256 lines, dev-build check, idle decision, start arguments, the two blocking network calls), `swap.rs` (exe swap through an `Ops` trait, tested with a fake), `changelog.rs` (parser). Decisions: ADR 0001 ("Updates").

- **Source**: `GET https://api.github.com/repos/wellbrained/ai-subhub/releases/latest` (User-Agent set, 20 s timeout, HTTPS only also across redirects). Tag `vX.Y.Z`; assets by name `ai-subhub.exe` and `ai-subhub.exe.sha256` (first token = hex digest, a file name after it is fine). Only a version newer than the running `CARGO_PKG_VERSION` is offered; a draft, pre-release, 404 or no release is "up to date", not an error. The repo must be public for unauthenticated checks.
- **Settings -> About & updates** (the former Updates page, merged with About on 2026-11-07): Update mode chips (Auto / Manual, default Manual), current version, "Last checked …" with **Check now**, and a status block: "Update available: vX.Y.Z" with **Install** (Auto: "Install now"), progress, or a safe error ("Could not check for updates: no connection", "Download failed: HTTP 404", "Cannot update in this folder: access is denied"). Saved on change as `updates { mode, last_check, last_seen_version }` (`#[serde(default)]`; test `older_files_without_updates_still_load`).
- **Schedule** (both modes): first check ~1 min after start, then every 6 h, 30 min after a failed one (`update::check_due`). Manual shows a tray balloon once per version. Auto downloads at once into `%LOCALAPPDATA%\AI SubHub\updates\ai-subhub-X.Y.Z.exe` (`.part` while loading; a verified copy is reused) and installs when `Busy` is idle, tried every minute.
- **Idle** (`update::Busy`, Auto only): no popover, Settings or Statistics window open, no sign-in running (`AppState::signing_in`), no popover top-edge drag (`AppState::popover_dragging`, only counts while the popover is open). A Manual Install ignores this.
- **Install**: download (or reuse) and verify SHA-256 (mismatch: file deleted, error shown) -> `<exe>.old` rename of the running exe -> copy the download to the original path -> start it with `--updated-from <old version> --wait-pid <pid>` -> quit. Copy failure rolls the rename back; if the new exe cannot start the swap is reverted and the old one keeps running. The new process waits for the pid (30 s) before the single-instance mutex and the tray, then deletes `<exe>.old` and stale files in the updates folder in a background thread. The exe path stays the same, so Start with Windows (HKCU Run) keeps working.
- **Development builds** (exe path has a `target` folder followed by `debug` or `release`, or the path is unknown): checking works, installing never; the page says "Development build: updates are off".
- **Patch notes**: `CHANGELOG.md` in the repo root, embedded with `include_str!`; `## X.Y.Z – date` plus 3-6 short bullets per version, `## Unreleased` ignored. Nothing opens at startup (owner, 2026-11-07: the old window "jumped in my face"). At start `AppState::prepare_whats_new` runs the core rule `update::whats_new` (`--updated-from` stands in for an empty `last_seen_version`): with notes between `last_seen_version` (exclusive) and the running version (inclusive) they wait in `AppState::pending_notes`; the **next time the popover opens** it draws a dialog over its content: a dim scrim (a click closes) and a rounded card (theme tokens, border, soft shadow) centred near the top with the title "Updated to vX.Y.Z", a muted "What's new" line, every version newest first with its heading and date, a scrollable body (max ~60% of the popover height, always-visible `vertical_scrollbar`) and a primary **Got it**. Absolutely positioned: the popover's fit-to-content height never changes. Got it, a scrim click or Esc closes it (Esc closes the dialog before the popover). `last_seen_version` is saved only when it is closed, so a popover closed without looking shows it again next time. A fresh install (empty value), a downgrade or no notes for the versions in between only records the version silently. Test flag: start with `--show-whats-new` to pretend the previous version was 0.1.0 (dialog on the next popover opening, nothing saved).
- **Release**: `scripts/release.ps1 -Version X.Y.Z [-Publish]` (see CLAUDE.md, "Releasing").
- Tests never touch the network, the real exe or the real updates folder; the swap order and rollback run against a fake file system.
